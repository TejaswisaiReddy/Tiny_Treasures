Why there are no screens here

This work is under NDA. So instead of screens, here’s the story.

01

The situation

A live product was moving to a new version. Every screen had to follow.

Nokia’s web application was migrating to a newer version of the product. The existing screens had to be updated to match — and every change had to fit a design system the whole team already depended on.

02

The real challenge

The new screens were the easy part. Making them feel like the old ones wasn’t.

Nokia’s product has a lot of screens, and more than one designer working on them. If the button I drew didn’t match the team’s button, the product would slowly stop feeling like one product. So anything new I built had to follow the rules the design system already used.

03

How I worked

  1. 01

    Work from the newest version as my reference

    I took the updated product version as the reference and rebuilt each screen in Figma to match it — checking every layout, state and label against it before calling a screen done.

  2. 02

    Reuse first, then build what’s missing

    I used the team’s existing tokens and library components wherever they fitted, and built new components where the newer version needed patterns the library didn’t cover yet — matching the system’s own rules so they belonged beside the originals.

  3. 03

    Talk to developers early

    I worked closely with developers and product colleagues on the smaller UI changes, instead of handing designs over at the end.

  4. 04

    Make accessibility checkable

    I contributed to the UX team’s accessibility documentation using WCAG 2.2 guidance, making requirements and review points clearer for everyone.

04

What I took from it

For me

Working inside real constraints, explaining design decisions clearly to developers, and contributing to a shared design system rather than around it.

For your team

I can join an enterprise product, learn its system quickly, and add to it without breaking it.
